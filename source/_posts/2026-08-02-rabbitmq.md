## 一、是什么 & 核心概念

### RabbitMQ 是什么

一句话：**基于 AMQP 协议的开源消息队列**，用 Erlang 写的，稳定、成熟、功能全。

### 干什么用

- **解耦**：A 服务不用直接调 B 服务，扔消息就行
- **异步**：用户下单后发短信/发邮件不用同步等
- **削峰**：秒杀 10 万请求，MQ 缓冲，后端慢慢消费

### 核心角色

```
Producer → Exchange → Binding → Queue → Consumer
（生产者）  （交换机）  （绑定规则） （队列）  （消费者）
```

| 角色 | 干什么 | 类比 |
| --- | --- | --- |
| Producer | 发消息 | 寄信人 |
| Exchange | 路由消息到队列 | 邮局分拣中心 |
| Binding | Exchange 和 Queue 的绑定规则 | 分拣规则 |
| Queue | 存消息 | 收件箱 |
| Consumer | 取消息处理 | 收信人 |
| Routing Key | 消息的路由标签 | 信封上的地址 |
| Broker | RabbitMQ 服务器本身 | 整个邮局 |

## 二、架构与工作流程

### 完整流程

```
1. Producer 发消息给 Exchange，带上 Routing Key
2. Exchange 根据类型 + Binding 规则，把消息路由到对应 Queue
3. Queue 存消息
4. Consumer 从 Queue 取消息消费
5. 消费成功后发 ACK，Queue 删除该消息
```

### AMQP 协议

RabbitMQ 的通信协议，定义了消息格式和交互流程。

```
应用程序 → AMQP客户端库(pika) → TCP连接 → RabbitMQ Broker
```

Python 用 **pika** 库通过 AMQP 和 RabbitMQ 通信：

```bash
pip install pika
```

### 最小示例：连接 RabbitMQ

```python
import pika

connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()
connection.close()

# 带账号密码
credentials = pika.PlainCredentials('admin', '123456')
connection = pika.BlockingConnection(
    pika.ConnectionParameters('localhost', 5672, '/', credentials)
)
```

## 三、Exchange 四种类型

这是 RabbitMQ 最核心的知识点：

### 1. Direct（直连）

**规则**：Routing Key **完全匹配**才路由。

```
消息 routing_key = "order.pay"
绑定 routing_key = "order.pay"    → ✅ 匹配
绑定 routing_key = "order.create" → ❌ 不匹配
```

```python
channel.exchange_declare(exchange='direct_ex', exchange_type='direct')
channel.queue_bind(queue='pay_queue', exchange='direct_ex', routing_key='order.pay')
channel.basic_publish(exchange='direct_ex', routing_key='order.pay', body='支付成功')
```

场景：点对点精确路由。

### 2. Fanout（扇出/广播）

**规则**：**忽略** Routing Key，消息发给所有绑定的队列。

```
消息 → Exchange → Queue1 ✅
                → Queue2 ✅
                → Queue3 ✅
```

```python
channel.exchange_declare(exchange='fanout_ex', exchange_type='fanout')
channel.queue_bind(queue='sms_queue', exchange='fanout_ex')
channel.queue_bind(queue='email_queue', exchange='fanout_ex')
channel.basic_publish(exchange='fanout_ex', routing_key='', body='广播通知')
```

场景：广播通知、所有服务都要收到。

### 3. Topic（主题）

**规则**：Routing Key **模式匹配**，支持通配符。

- ：匹配**一个**词
- `#`：匹配**零或多个**词

```
消息 routing_key = "order.pay.success"
绑定 "order.#"         → ✅ 匹配
绑定 "order.*.success"  → ✅ 匹配
绑定 "user.#"          → ❌ 不匹配
```

```python
channel.exchange_declare(exchange='topic_ex', exchange_type='topic')
channel.queue_bind(queue='all_order_queue', exchange='topic_ex', routing_key='order.#')
channel.basic_publish(exchange='topic_ex', routing_key='order.pay.success', body='支付成功')
```

场景：灵活的分类订阅，**最常用**。

### 4. Headers（头匹配）

**规则**：根据消息 Header 里的键值对匹配，不用 Routing Key。

```python
channel.queue_bind(queue='vip_queue', exchange='headers_ex', routing_key='',
    arguments={'x-match': 'all', 'level': 'vip', 'region': 'cn'})
```

很少用，性能也差，了解即可。

### 速记表

| 类型 | 路由规则 | 场景 |
| --- | --- | --- |
| Direct | 精确匹配 | 指定消费者 |
| Fanout | 广播全部 | 通知所有人 |
| Topic | 通配匹配 | 灵活订阅 |
| Headers | Header匹配 | 几乎不用 |

## 四、Queue 队列

### 队列属性

| 属性 | 说明 |
| --- | --- |
| queue | 队列名 |
| durable | 持久化（重启不丢） |
| exclusive | 独占（仅当前连接可用，断开自动删除） |
| auto_delete | 最后一个消费者断开后自动删除 |
| arguments | 额外参数（TTL、死信、最大长度等） |

### 声明队列

```python
# 持久队列（生产用）
channel.queue_declare(queue='order_queue', durable=True, exclusive=False, auto_delete=False)

# 临时队列（用完即扔，名字随机）
result = channel.queue_declare(queue='', exclusive=True)
temp_queue = result.method.queue
```

### 队列参数

```python
channel.queue_declare(queue='bounded_queue', durable=True, arguments={
    'x-max-length': 10000,           # 最多存1万条
    'x-max-length-bytes': 104857600, # 最多占100MB
    'x-overflow': 'reject-publish',  # 满了拒绝新消息（默认丢弃最旧的）
    'x-queue-type': 'quorum',        # 仲裁队列
})
```

## 五、消息确认机制

### 消费者确认（ACK）

消息发给消费者后，RabbitMQ **不会立刻删除**，要等消费者确认：

| 模式 | 说明 | 用法 |
| --- | --- | --- |
| 自动 ACK | 发出去就删 | 不可靠，消费者挂了消息就丢了 |
| 手动 ACK | 消费者处理完后主动确认 | **推荐** |
| 拒绝（NACK/Reject） | 处理失败，可选重新入队 | 异常场景 |

```python
def callback(ch, method, properties, body):
    try:
        process(body)
        ch.basic_ack(delivery_tag=method.delivery_tag)              # 确认
    except Exception:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True) # 拒绝并重入队

# auto_ack=False 表示手动确认模式
channel.basic_consume(queue='order_queue', on_message_callback=callback, auto_ack=False)
```

**拒绝且不重入队**（消息进死信）：

```python
ch.basic_reject(delivery_tag=method.delivery_tag, requeue=False)
```

### 生产者确认（Confirm）

生产者怎么知道消息到了 RabbitMQ？

```python
channel.confirm_delivery()  # 开启confirm模式

try:
    channel.basic_publish(exchange='', routing_key='queue', body='数据',
        properties=pika.BasicProperties(delivery_mode=2), mandatory=True)
except pika.exceptions.UnroutableError:
    print('消息无法路由')
except pika.exceptions.NackError:
    print('消息被RabbitMQ拒绝')
```

## 六、持久化

消息不丢失需要**三重保障**：

| 层级 | 怎么做 |
| --- | --- |
| Exchange 持久化 | `durable=True` |
| Queue 持久化 | `durable=True` |
| 消息持久化 | `delivery_mode=2` |

```python
channel.exchange_declare(exchange='order_ex', exchange_type='direct', durable=True)  # ①
channel.queue_declare(queue='order_queue', durable=True)                              # ②
channel.basic_publish(exchange='order_ex', routing_key='order', body='数据',
    properties=pika.BasicProperties(delivery_mode=2))                                 # ③
```

> 三个都设了才能保证重启不丢消息。但仍有极端情况（写入磁盘前断电），需要配合 Confirm 机制。
>

## 七、死信队列 & 延迟队列

### 死信队列（DLX）

消息"死了"后去的地方。

**什么时候变死信**：

1. 消费者拒绝（reject/nack）且 `requeue=False`
2. 消息过期（TTL 到了没人消费）
3. 队列满了（超过 max-length）

```python
# 1. 声明死信交换机和队列
channel.exchange_declare(exchange='dlx_exchange', exchange_type='direct')
channel.queue_declare(queue='dlx_queue', durable=True)
channel.queue_bind(queue='dlx_queue', exchange='dlx_exchange', routing_key='dlx_key')

# 2. 正常队列绑定死信
channel.queue_declare(queue='normal_queue', durable=True, arguments={
    'x-dead-letter-exchange': 'dlx_exchange',
    'x-dead-letter-routing-key': 'dlx_key',
})
```

场景：消费失败的消息集中处理、重试、人工排查。

### 延迟队列

RabbitMQ 没有原生延迟队列，两种实现：

**方式一：TTL + 死信**

```python
channel.queue_declare(queue='delay_queue', durable=True, arguments={
    'x-message-ttl': 30000,                   # 30秒过期
    'x-dead-letter-exchange': 'dlx_exchange',
    'x-dead-letter-routing-key': 'process_key',
})
# 消息发到 delay_queue → 30秒后过期进死信 → 消费者从死信队列消费
```

**方式二：延迟插件（推荐）**

```bash
rabbitmq-plugins enable rabbitmq_delayed_message_exchange
```

```python
channel.exchange_declare(exchange='delayed_ex', exchange_type='x-delayed-message',
    arguments={'x-delayed-type': 'direct'})

channel.basic_publish(exchange='delayed_ex', routing_key='key', body='30秒后执行',
    properties=pika.BasicProperties(headers={'x-delay': 30000}))
```

场景：订单30分钟未支付自动取消、延迟通知、定时重试。

## 八、消息幂等性

**问题**：网络闪断导致消息重复消费怎么办？

**核心思想**：消费者处理消息做**幂等控制**，多次处理结果和一次一样。

| 方案 | 做法 |
| --- | --- |
| 唯一ID + 去重表 | 消费前查数据库，处理过就跳过 |
| Redis SETNX | `SETNX msg:{id} 1`，设置成功才处理 |
| 数据库唯一约束 | 插入重复报错就忽略 |
| 乐观锁/版本号 | `UPDATE ... WHERE version = N` |

```python
import redis, uuid
r = redis.Redis()

# 发消息带唯一ID
channel.basic_publish(exchange='', routing_key='queue', body='内容',
    properties=pika.BasicProperties(message_id=str(uuid.uuid4()), delivery_mode=2))

# 消费时判重
def callback(ch, method, properties, body):
    msg_id = properties.message_id
    if r.set(f'msg:{msg_id}', '1', nx=True, ex=3600):  # 设置成功=没处理过
        process(body)
    ch.basic_ack(delivery_tag=method.delivery_tag)
```

## 九、消息顺序性

### 问题

一个队列多个消费者 → 消息可能乱序处理。

### 解决方案

| 方案 | 做法 | 缺点 |
| --- | --- | --- |
| 单消费者 | 一个队列只一个消费者 | 吞吐低 |
| 分区消费 | 同一业务ID路由到同一队列 | 需要设计routing |
| 消息内排序 | 消息带序号，消费者本地排序 | 复杂 |

**最常用**：按 user_id hash 路由到固定队列：

```python
import hashlib

def get_routing_key(user_id, num_queues=4):
    h = int(hashlib.md5(str(user_id).encode()).hexdigest(), 16)
    return f'order.queue.{h % num_queues}'

channel.basic_publish(exchange='order_ex', routing_key=get_routing_key(1001), body='订单')
```

## 十、高可用（集群 & 镜像队列 / 仲裁队列）

### 普通集群

- 多个 RabbitMQ 节点共享**元数据**（Exchange、Queue 定义、Binding）
- 但消息**只存在一个节点**
- 其他节点收到请求会**转发**到消息所在节点
- 某节点挂了，上面的消息就**丢了**

### 镜像队列（经典HA，3.8之前）

消息在多个节点上有**副本**，master 挂了自动切换：

```bash
rabbitmqctl set_policy ha-all ".*" '{"ha-mode":"all"}'
rabbitmqctl set_policy ha-two ".*" '{"ha-mode":"exactly","ha-params":2}'
```

### 仲裁队列（Quorum Queue，3.8+ 推荐）

基于 **Raft 共识算法**，比镜像队列更可靠：

```python
channel.queue_declare(queue='quorum_queue', durable=True,
    arguments={'x-queue-type': 'quorum'})
```

| 维度 | 镜像队列 | 仲裁队列 |
| --- | --- | --- |
| 算法 | 主从复制 | Raft 共识 |
| 数据安全 | 可能丢 | 多数确认不丢 |
| 性能 | 一般 | 更好 |
| 推荐 | 旧版本 | **新项目用这个** |

### Python 连接集群

```python
params = [pika.ConnectionParameters('rabbit1'),
          pika.ConnectionParameters('rabbit2'),
          pika.ConnectionParameters('rabbit3')]
connection = pika.BlockingConnection(params)  # 自动选一个可用节点
```

## 十一、流控与限流

### 消费者预取（Prefetch）

限制消费者一次拿多少条未确认消息：

```python
channel.basic_qos(prefetch_count=10)  # 一次最多10条未ACK的消息
```

不设 prefetch → 消息全推给消费者 → 消费者内存爆掉。

**推荐值**：根据消费速度设，一般 10-100。

### 全局 vs 单消费者

```python
channel.basic_qos(prefetch_count=10, global_qos=False)  # 每个消费者10条（默认）
channel.basic_qos(prefetch_count=100, global_qos=True)  # 整个Channel共100条
```

### 生产者流控

RabbitMQ 内存或磁盘到阈值 → 自动阻塞生产者（Connection Blocked）。

```
# rabbitmq.conf
vm_memory_high_watermark.relative = 0.4   # 内存超过40%触发流控
disk_free_limit.absolute = 50MB           # 磁盘剩余低于50MB触发流控
```

Python 端可监听阻塞事件：

```python
connection.add_on_connection_blocked_callback(lambda conn, method: print('被流控了！'))
connection.add_on_connection_unblocked_callback(lambda conn, method: print('流控解除'))
```

## 十二、事务与 Confirm

### 事务模式

```python
channel.tx_select()   # 开启事务
try:
    channel.basic_publish(exchange='', routing_key='queue', body='消息')
    channel.tx_commit()   # 提交
except Exception:
    channel.tx_rollback() # 回滚
```

**问题**：性能极差（同步阻塞），吞吐降 250 倍。**不推荐用**。

### Confirm 模式（推荐）

```python
channel.confirm_delivery()
try:
    channel.basic_publish(exchange='', routing_key='queue', body='消息',
        properties=pika.BasicProperties(delivery_mode=2), mandatory=True)
except pika.exceptions.UnroutableError:
    print('无法路由，需要重发')
except pika.exceptions.NackError:
    print('RabbitMQ拒绝，需要重发')
```

性能比事务好得多，是**生产环境保证消息不丢的标准方案**。

## 十三、TTL（消息/队列过期）

### 消息级 TTL（每条消息不同过期时间）

```python
channel.basic_publish(exchange='', routing_key='queue', body='60秒后过期',
    properties=pika.BasicProperties(expiration='60000'))  # 毫秒
```

### 队列级 TTL（队列内所有消息统一过期时间）

```python
channel.queue_declare(queue='ttl_queue', durable=True,
    arguments={'x-message-ttl': 60000})
```

| 维度 | 消息TTL | 队列TTL |
| --- | --- | --- |
| 粒度 | 每条消息不同 | 队列内统一 |
| 检查时机 | 消费时检查 | 队首检查 |
| 性能 | 稍差 | 好 |

### 队列自身的过期

```python
channel.queue_declare(queue='auto_expire_queue',
    arguments={'x-expires': 1800000})  # 队列30分钟没人用就自动删除
```

过期消息如果配了死信 → 自动进死信队列。

## 十四、优先级队列

让重要消息先被消费：

```python
# 声明队列支持优先级
channel.queue_declare(queue='priority_queue', durable=True,
    arguments={'x-max-priority': 10})

# 发高优先级消息
channel.basic_publish(exchange='', routing_key='priority_queue', body='VIP消息',
    properties=pika.BasicProperties(priority=9))  # 0-10，数字越大越优先
```

注意：只有**消息积压时**优先级才有意义，消费快的话没效果。

## 十五、惰性队列（Lazy Queue）

```python
channel.queue_declare(queue='lazy_queue', durable=True,
    arguments={'x-queue-mode': 'lazy'})
```

| 模式 | 存储 | 速度 | 内存 |
| --- | --- | --- | --- |
| 普通队列 | 尽量存内存 | 快 | 占多 |
| 惰性队列 | 直接存磁盘 | 稍慢 | 省 |

**用途**：消息量巨大、消费慢、不想 OOM 时使用。

## 十六、连接与 Channel

```
Application → Connection（TCP连接）→ Channel1
                                   → Channel2
                                   → Channel3
```

- **Connection**：一个 TCP 连接，创建开销大
- **Channel**：连接内的虚拟通道，轻量级

```python
connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel1 = connection.channel()  # 生产者用
channel2 = connection.channel()  # 消费者用
```

**最佳实践**：

- 一个应用 **1-2 个 Connection**
- 每个线程用**独立的 Channel**
- pika 的 BlockingConnection **不是线程安全**的，多线程要每个线程自己建连接

### 心跳

```python
connection = pika.BlockingConnection(
    pika.ConnectionParameters('localhost', heartbeat=600))  # 防被断开
```

## 十七、Virtual Host

类似命名空间/租户隔离：

```bash
rabbitmqctl add_vhost /production
rabbitmqctl add_vhost /testing
rabbitmqctl set_permissions -p /production admin ".*" ".*" ".*"
```

Python 连接指定 VHost：

```python
connection = pika.BlockingConnection(pika.ConnectionParameters(
    host='localhost', virtual_host='/production',
    credentials=pika.PlainCredentials('admin', '123456')))
```

- 不同 VHost 的 Exchange/Queue 完全隔离
- 一个 RabbitMQ 实例给多个项目用时，按 VHost 隔离
- 默认 VHost 是 `/`

### 完整消费者

```python
import pika, json

credentials = pika.PlainCredentials('admin', '123456')
connection = pika.BlockingConnection(
    pika.ConnectionParameters('localhost', 5672, '/', credentials, heartbeat=600))
channel = connection.channel()
channel.exchange_declare(exchange='order_exchange', exchange_type='topic', durable=True)
channel.queue_declare(queue='order_queue', durable=True, arguments={
    'x-dead-letter-exchange': 'dlx_exchange', 'x-max-length': 10000})
channel.queue_bind(queue='order_queue', exchange='order_exchange', routing_key='order.#')
channel.basic_qos(prefetch_count=10)

def callback(ch, method, properties, body):
    try:
        data = json.loads(body)
        process_order(data)
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

channel.basic_consume(queue='order_queue', on_message_callback=callback, auto_ack=False)
channel.start_consuming()
```

## 二十、与 Kafka / RocketMQ 对比

| 维度 | RabbitMQ | Kafka | RocketMQ |
| --- | --- | --- | --- |
| 语言 | Erlang | Scala/Java | Java |
| 协议 | AMQP | 自定义 | 自定义 |
| 吞吐量 | 万级 | **百万级** | 十万级 |
| 延迟 | **微秒级** | 毫秒级 | 毫秒级 |
| 消息模型 | Exchange 路由 | 分区日志 | Topic + Tag |
| 消费模式 | Push 为主 | Pull | Push + Pull |
| 消息回溯 | 不支持 | **支持** | 支持 |
| 事务消息 | 不支持 | 支持 | **完善** |
| 延迟消息 | 插件/TTL | 不原生 | **原生支持** |
| 顺序消息 | 单队列有序 | 分区内有序 | 分区内有序 |
| 管理界面 | 自带 | 需第三方 | 自带 |
| Python生态 | pika / celery | confluent-kafka | rocketmq-client |
| 适合场景 | 企业级路由/可靠投递 | 大数据/日志/流处理 | 电商/金融 |

### 怎么选

- **业务消息、路由复杂、可靠性要求高** → RabbitMQ
- **大数据量、日志采集、流处理** → Kafka
- **电商/金融、事务消息、延迟消息** → RocketMQ
- **Python 异步任务** → RabbitMQ + Celery（最成熟的组合）
- **简单异步、团队小** → RabbitMQ（上手最快）

## 二十一、生产环境最佳实践

### 消息不丢失清单

```
生产者 → RabbitMQ → 消费者
  ①          ②         ③
```

| 阶段 | 保证手段 |
| --- | --- |
| ① 发送不丢 | Confirm 机制 + 失败重试 |
| ② 存储不丢 | Exchange / Queue / 消息都持久化 |
| ③ 消费不丢 | 手动 ACK + 处理完再确认 |

### 连接管理

- 用连接池或长连接，不要频繁创建/关闭
- Channel 按线程分配，不共用
- 设置心跳（默认 60 秒）防止被断开
- pika.BlockingConnection 不是线程安全的

### 队列设计

- 队列名有业务含义：`order.pay.queue`
- 生产和消费两端都声明队列（防一方先启动报错）
- 设置队列最大长度，防无限堆积
- 配置死信队列兜底

### 监控告警

| 指标 | 告警阈值 |
| --- | --- |
| 队列消息堆积 | > 10000 条 |
| 消费者数量 | = 0（无消费者） |
| 连接/Channel 数 | 接近上限 |
| 内存使用率 | > 40%（流控线） |
| 磁盘剩余 | < 200MB |
| 消息投递/消费速率 | 异常波动 |

```python
import requests
r = requests.get('<http://localhost:15672/api/queues>', auth=('admin', '123456'))
for q in r.json():
    if q.get('messages', 0) > 10000:
        print(f"⚠️ 队列 {q['name']} 堆积 {q['messages']} 条!")
    if q.get('consumers', 0) == 0 and q.get('messages', 0) > 0:
        print(f"⚠️ 队列 {q['name']} 无消费者!")
```

### 避坑清单

| 坑 | 解决 |
| --- | --- |
| 消息堆积 OOM | 设 max-length + 惰性队列 |
| 重复消费 | 消费者做幂等（Redis SETNX） |
| 消费者挂了消息丢失 | 手动 ACK |
| 队列过多性能差 | 合并队列，用 routing key 区分 |
| 大消息阻塞 | 消息体 < 1MB，大文件传引用 |
| 重启后消息丢 | 三重持久化 |
| 消息乱序 | 同业务ID路由到同一队列 |
| 连接被断开 | 设心跳 + 重连逻辑 |
| pika 多线程崩 | 每个线程独立连接 |

### 重连示例

```python
import pika, time

def connect_with_retry(max_retries=10):
    for i in range(max_retries):
        try:
            return pika.BlockingConnection(pika.ConnectionParameters('localhost'))
        except pika.exceptions.AMQPConnectionError:
            wait = min(2 ** i, 30)
            print(f'连接失败，{wait}秒后重试...')
            time.sleep(wait)
    raise Exception('无法连接RabbitMQ')
```
